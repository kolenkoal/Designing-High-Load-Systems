# Отчёт: бенчмарк FastAPI API Gateway

## 1. Что было сделано

Создан минимальный воспроизводимый стенд в `bench_gateway/` для измерения колена насыщения async FastAPI proxy на 1 vCPU.

**Артефакты:**

| Файл | Назначение |
|---|---|
| `mock_auth.py` | FastAPI `:8001`, `GET /auth`, `asyncio.sleep(0.003)` |
| `mock_downstream.py` | FastAPI `:8002`, `GET /api/ping`, `asyncio.sleep(0.003)` |
| `gateway.py` | FastAPI `:8000`, `GET /ping` → последовательно вызывает auth и downstream через один общий `httpx.AsyncClient` (создаётся в lifespan) |
| `Dockerfile` | python:3.12-slim + fastapi + uvicorn + httpx |
| `docker-compose.yml` | 3 сервиса, каждый пиннен через `cpuset` к отдельному ядру (0/1/2), 1 uvicorn worker |
| `bench.sh` | Прогон `hey` на уровнях 1/5/10/20/50/100/200 × 10s, парсит rps + p50/p95/p99 в `results.csv` |
| `plot.py` | Два графика matplotlib → `results.png` |
| `README.md` | Инструкция запуска |

## 2. Что пошло не так по ходу и как чинилось

| # | Симптом | Причина | Фикс |
|---|---|---|---|
| 1 | `pip install` в Docker падал с `SSL: CERTIFICATE_VERIFY_FAILED` | Корпоративный MITM с self-signed CA, которому pip внутри контейнера не доверяет | В Dockerfile добавлены `--trusted-host pypi.org files.pythonhosted.org pypi.python.org` |
| 2 | `bash bench.sh` молча выходил после первой итерации | `set -euo pipefail` + `grep`, который ничего не находит, валит весь скрипт | Убран `-e`, добавлена функция `extract()` с дефолтом `0` и диагностикой |
| 3 | `plot.py` падал в `tight_layout` с *"Data has no positive values, and therefore cannot be log-scaled"* | После п.2 в `results.csv` остался только заголовок → пустые ряды → log-scale валится | `safe_xscale` / `safe_yscale` включают логарифм только если все значения положительны |
| 4 | Прогон прошёл, но p50/p95/p99 везде = 0 | Эта версия `hey` печатает `50%% in 0.0086 secs` (двойной процент). Мой паттерн `"50% in"` совпадений не находил | Заменено на регэксп `^[[:space:]]*50%+ in` |

## 4. Интерпретация

**Теоретический потолок при последовательных вызовах:** каждый запрос ждёт `3 ms (auth) + 3 ms (downstream) = 6 ms` чистого I/O. С учётом httpx + JSON + цикл событий — фактическая стоимость одного запроса в районе 12–14 ms (видно по p50 при низкой concurrency).

**Колено насыщения** — между **c=10 и c=20**:
- До c=10 RPS растёт почти линейно (70 → 393 → 733), p50 держится ~13 ms.
- На c=20 RPS уже падает (704), а p50 удваивается до 25 ms, p99 = 73 ms — это классический признак того, что воркер начинает не успевать.
- Дальше — деградация: c=200 даёт всего 347 rps при p99 = 1.7 секунды (queueing).

**Пик** ≈ **733 rps** при c=10–20. Это та самая физическая ёмкость одного async-worker'а на 1 vCPU для данного профиля нагрузки.

Форма кривой типична для CPU-bound async-сервера: RPS растёт до точки, где event loop полностью занят (CPU 100%), а после — выходит на плато и снижается из-за роста очередей и overhead httpx-клиента.

## 5. Оговорки

- **macOS Docker Desktop**: `cpuset` в docker-compose не пробрасывается на физические ядра — контейнеры крутятся в Linux VM, которая сама решает шедулинг. Поэтому «1 vCPU» здесь — приближение. Для чистого результата нужно запускать на Linux-хосте.
- **Вызовы последовательные**: gateway делает auth → downstream строго по очереди. Если поменять на `asyncio.gather(...)` — нижняя граница латентности упадёт вдвое (3 ms вместо 6 ms), и пик RPS вырастет.
- **httpx vs aiohttp**: httpx удобнее, но на CPU тяжелее. Замена на aiohttp типично даёт +20–40% rps на этом профиле.
- **Длительность 10 s на уровень** — короткая. Для решений по capacity-planning лучше брать 60–120 s, чтобы исключить транзиенты и JIT-разогрев.
- **`hey` сам потребляет CPU** на той же машине. На c=200 часть деградации может быть от нагрузчика, а не от gateway. Идеальный сетап — нагрузчик на отдельной машине.

## 6. Что можно сделать дальше

1. Прогнать те же уровни на Linux-хосте с реально работающим `cpuset` — сравнить.
2. Добавить вариант gateway с `asyncio.gather` — посмотреть, как сдвинется колено.
3. Заменить httpx на aiohttp в gateway — измерить разницу в RPS при том же CPU.
4. Увеличить duration до 60 s и добавить ramp-up для более стабильных p99.
5. Снять CPU-профиль gateway (`py-spy` / `austin`) на пике, чтобы понять, на что уходит CPU — сериализация JSON, httpx, или сам uvicorn.
